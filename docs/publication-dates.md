# 发布时间筛选

0.3.0 增加 `preferences.publishedWithinDays`，默认 null 不限制。设置 30 表示按北京时间取包含今天的最近 30 个自然日，例如 2026-10-15 筛选时窗口为 2026-09-16 至 2026-10-15。重新导出按本次筛选日期计算，摘要记录 evaluatedAt 和窗口，旧导出不覆盖。

```json
{
  "preferences": {
    "publishedWithinDays": 30
  }
}
```

该片段应合并到实际完整配置。也可在采集或导出时使用 `--published-within-days 30`。旧批次导出只使用已保存证据；需要重新访问详情补字段时使用 `collect --resume "批次ID" --phase details --refresh-details`。

## 证据与分组

- 明确发布时间在窗口内：通过该项条件，其他资格、薪资和正文条件仍需满足。
- 明确发布时间在窗口外：已排除，保留原始记录与原因。
- 缺少日期、日期无法解析、来源冲突或发布时间晚于筛选时刻：待核实；如同时有其他明确不符合条件，则优先已排除。

接受适配器提取的明确 publishTime／publishDate／datePosted 字段、同一岗位的 JobPosting.datePosted 或明确“发布时间／发布日期／发布于”标签。页面元数据和正文的岗位 URL 必须匹配；JobPosting 还需核对标题。列表与接口字段只在既有岗位身份检查通过后使用。

日期保留原文、来源、观测时刻。支持完整年月日、带时区时间戳、Unix 秒／毫秒，以及基于原观测时刻解析的“昨天／N 天前”；不猜测省略年份的日期，不把相对日期在导出时重新向后滚动。相同岗位出现互相矛盾的发布日期时保留冲突，不自动采用更新的一个。

| 字段 | 含义 | 可用于新挂岗位条件 |
| --- | --- | --- |
| publishedAt | 岗位发布日期 | 是，需来源明确且有效 |
| jobUpdatedAt | 岗位更新时间 | 否，旧岗位也可能更新 |
| pageUpdatedAt | 页面更新时间，例如 Baidu upDate | 否 |
| firstSeenAt | 本数据库跨批次首次观察到该岗位的时间 | 否，首次抓到不等于首次发布 |
| collectedAt | 当前采集记录的观测时间 | 否 |

招聘者活跃时间、在线状态、搜索排名、createTime 或泛化刷新字段不能证明新发布。日期解析正确也只能反映平台标注，不能证明从未重发、招聘者一定回复或当前仍有名额。[Schema.org datePosted](https://schema.org/datePosted) 将其定义为在线刊登的发布日期，本程序据此区分发布与页面更新。

## 当前 BOSS 适配范围

2026-10-15 做了少量真实只读复查：一个详情页的可见“页面更新时间”、Baidu JSON-LD upDate 和页面更新元字段均不能证明岗位发布时间；一次列表响应没有 publishTime／publishDate／datePosted 等可靠发布字段。随后重读一个三岗验证批次，取得两条完整正文、一条公司身份字段不足；没有取得可核对的发布日期。

因此，当前观察到的 BOSS 路径不能保证获取“30 天内新挂”的岗位。功能会如实提示缺失并分入待核实。明确发布日期字段和 JobPosting 路径由虚构离线样例覆盖，不能把这些样例视为平台当前实际返回了这些字段。刷新旧数据也不保证补到日期。

若未来需要“最近发现的线索”，可另做首次发现条件，但必须单独命名。多次采集建立的观察历史不能追溯程序启用前的首次上架时间。
